# Real Estate Backend — Project Instructions

Multi-tenant real estate agency platform (FastAPI + PostgreSQL/PostGIS + Redis).
The full blueprint is in [project.md](project.md) — follow it. The build plan is
incremental: one part at a time, never everything at once.

**Codebase context:** `graphify-out/` has the knowledge graph — query it before searching from scratch.

## Per-part workflow

1. Run checks: `uv run pytest` + `uv run ruff check` + `uv run mypy` — all green.
2. Update the **Build progress log** below.
3. Commit.

Code review and graph updates are done manually by the user — don't run them automatically.

## Architecture rules (from project.md §5 — enforced in review)

- Modular monolith under `src/app/modules/<name>/` with `models.py / schemas.py / repository.py / service.py / router.py`.
- Routers never touch the DB: routers → services → repositories.
- Modules never import another module's `models.py`/`repository.py` — call its service or subscribe to its events.
- Every repository method takes `tenant_id`. No exceptions. Postgres RLS is the safety net, not the only guard.
- API responses use explicit `*Out` schemas (`app.core.schema.OutSchema`); inputs use `InputSchema` (`extra="forbid"`).
- Errors leave the API only as RFC 9457 problem+json (raise `AppError` subclasses from `app.core.exceptions`).
- camelCase JSON on the wire, snake_case in Python; cursor pagination (`app.core.pagination`) for all list endpoints.
- Anything > ~200ms of work goes to a background worker (Celery, from Part 5 on).

## Commands

- Deps: `uv sync` · Add dep: `uv add <pkg>`
- Stack: `docker compose -f docker/docker-compose.yml up -d --wait` (Postgres+PostGIS :5432, Redis :6379, Mailpit UI :8025)
- Run: `uv run uvicorn app.main:app --reload --port 8000`
- Worker: `uv run celery -A app.workers.celery_app worker --loglevel info -Q default,media,sync,analytics`
- Beat: `uv run celery -A app.workers.celery_app beat --loglevel info`
- Tests: `uv run pytest` (needs the docker stack; uses `realestate_test` DB + Redis db 1; Celery runs in eager mode, no worker/beat process needed)
- Lint/types: `uv run ruff check` · `uv run ruff format` · `uv run mypy`
- Migrations: `uv run alembic revision --autogenerate -m "..."` then hand-review; `uv run alembic upgrade head`
- The app connects as non-superuser `app_user` (RLS applies); Alembic uses `DATABASE_DDL_URL` (postgres role).
- **Prod deploy (§16, Part 25):** build the image `docker build -f docker/Dockerfile -t real-estate-backend:latest .`; run the full app stack (app+worker+beat+Caddy over the backing services) `docker compose -f docker/docker-compose.yml -f docker/docker-compose.prod.yml up -d --build`. One image, three roles (`entrypoint.sh` arg: `api`|`worker`|`beat`); the `api` role runs `alembic upgrade head` on startup (set `RUN_MIGRATIONS=0` on non-migrating replicas). Env comes from `.env` (see `.env.example`).

- **Part 28 — Edge security hardening (§10.1–§10.2, done, 2026-07-24):** hardens the request edge; no new module, migration, or permission — three core concerns (`middleware.py`, a new `core/cors.py`, a rewritten `core/rate_limit.py`) plus the auth router's per-endpoint limits. **HSTS + CSP** in `SecurityHeadersMiddleware`, which now takes `Settings` and precomputes its header list per scope. HSTS is **deliberately conditional**: emitted when `app_env` is staging/production (TLS terminates at Caddy) *or* the request itself arrived over https, never on plain-http local dev — a `max-age` cached from `http://localhost` would pin the developer's own browser to https for a year, a self-inflicted outage. Caddy already sets HSTS at the edge and its `header` directive **replaces** rather than appends, with the values kept identical, so this is defence-in-depth rather than a duplicated header — the app's copy survives a proxy misconfiguration and the edge's copy survives an app one. **CSP is split in two**: `API_CSP` (`default-src 'none'` + `frame-ancestors`/`base-uri`/`form-action 'none'`) on everything, since a JSON payload has nothing to load and a browser tricked into rendering one as HTML must not be able to fetch anything; `DOCS_CSP` on `/docs`+`/redoc`+`/openapi.json`, default-deny plus exactly what Swagger UI needs. The Swagger allowances were **read out of the installed FastAPI rather than guessed** — `openapi/docs.py` pins `cdn.jsdelivr.net/npm/swagger-ui-dist@5` for the JS+CSS and `fastapi.tiangolo.com` for the favicon, and the UI fetches `/openapi.json` same-origin (covered by `connect-src 'self'`); `'unsafe-inline'` is needed because Swagger's bootstrap is an inline script/style, which is exactly why the policy is scoped to the docs paths instead of applied globally.

  **Dynamic tenant-aware CORS** (`core/cors.py`) replaces Starlette's static `CORSMiddleware`. A static list could never be right here: agency domains are rows in `tenant_domains` that change with every onboarding and no restart, and listing them all in one env var would let agency A's site make *credentialed* cross-origin calls to agency B's API host — the exact thing CORS exists to stop. So the allowlist is resolved per request: the request's own tenant from `Host`, the `Origin`'s host the same way, both through the **existing Redis-cached `DomainTenantResolver`** (two cached lookups, no new query and no new cache), and the origin is reflected **only when both resolve to the same tenant id**. `cors_origins` survives as the **additive** allowlist for origins belonging to no tenant (the platform back-office SPA, local dev frontends), matched exactly and **never widened to `*`** — `*` alongside `Access-Control-Allow-Credentials` is both spec-forbidden and precisely what would make every agency site readable by any page on the internet. `Vary: Origin` is always set so a shared cache cannot hand one tenant's response to another's origin. **Deliberate scope call — CORS does not require `verification_status == verified`**, despite the part prompt's wording: domains are created `PENDING` and only flip to `VERIFIED` after the DNS TXT sweep, while the *tenant middleware already serves traffic* on an unverified domain — so a verified-only rule would break the browser for every newly-onboarded agency while its API kept working, a confusing half-outage. A domain is only in the table because the platform put it there, so **tenant ownership, not DNS proof, is the property that matters** for "may this origin read this tenant's API"; DNS verification exists to gate *certificate issuance* (§16's on-demand-TLS ask handler), a different question. Preflights are **answered in the middleware and never forwarded** (an `OPTIONS` carries no credentials and no tenant expectation; forwarding it would make every preflight hit tenant resolution and the router for nothing); a rejected preflight is a **403 rather than a silent 200 with no CORS headers** — the browser blocks either way, but the network log tells the truth.

  **Layered rate limits** (§10.2): `core/rate_limit.py` was refactored so both layers share one `consume()` sliding-window-log primitive (a sorted set of hit timestamps — a fixed-window *counter* would let a caller spend a full budget at the end of one window and another at the start of the next, passing twice the limit across the boundary), which now also computes a real `Retry-After` from when the oldest hit in the window ages out. `GlobalRateLimitMiddleware` is a coarse per-IP budget (300/min) mounted **above CORS and tenant resolution**, so a flood aimed at an unknown host or a nonexistent path costs one Redis lookup instead of a tenant lookup plus routing; `/healthz`, `/readyz` and `/internal` are exempt, because a load balancer polling on a fixed interval would otherwise end up rate-limiting its own health check. Per-endpoint limits land on `login`/`register`/`refresh`/`password-reset` via a new `auth_rate_limit(action, limit)` helper — the `rate_limit` factory whose docstring since Part 8 said auth "can adopt later without rework", and it did, with no rework. Keyed **per action** so exhausting login does not also lock the caller out of password reset, and **deliberately not keyed on the submitted email**: an attacker controls that field so it is free to rotate, and keying on it would let them lock a victim out of their *own* reset flow. `refresh` gets 3× the budget (a legitimate every-15-minutes call several tabs may issue at once). `RateLimitedError`'s `retry_after` kwarg is now **promoted to the standard `Retry-After` header** by the `AppError` handler as well as appearing in the problem body, so a client that understands only the header still backs off. **Platform auth (`/platform/auth/*`) deliberately gets no per-endpoint limit** — that router is tenant-exempt and every limit here is keyed on tenant+IP; it is covered by the global budget, and a tenant-free key scheme is worth inventing alongside Part 29's account lockout rather than bolting on a second keying convention now (documented at the router). Both layers **degrade open** — an availability-over-enforcement trade stated explicitly in the module docstring, since the limiter exists to blunt abuse and is *not* the last line in front of an account (that is Part 29's lockout).

- **Part 30 — Data-protection primitives: field encryption + Idempotency-Key (§10.7, §9, done, 2026-07-24):** two reusable security primitives, built ahead of Part 29 per the dependency ordering (MFA field-encrypts its TOTP secret with the helper here). New dep `cryptography`; no new module, migration, or permission. **`core/crypto.py`** — AES-256-GCM field encryption. `FieldCipher` stretches `field_encryption_key` through SHA-256 once (same "not a raw passphrase" stance as JWT/HMAC signing elsewhere), encrypts with a random 96-bit nonce per call (AEAD-authenticated — a tampered ciphertext raises rather than decrypting to garbage), and stores `{key_id}:{b64(nonce+ciphertext)}`. **Key-rotation-ready**: `field_encryption_key_id` names the *current* key for new writes; `field_encryption_keys` (a `id=key,id=key` map, separate from the current key) keeps retired keys in the keyring so already-encrypted rows keep decrypting after a rotation — `EncryptedString` (a `String` `TypeDecorator`) only provides the read/write primitive, not a re-encrypt-on-rotate job. **Deliberately takes no `Settings` at construction**: SQLAlchemy columns are declared at class-body (import) time, long before a `Settings` instance exists, so the type decorator resolves the process-wide cipher lazily via `get_settings()` — the same `lru_cache` singleton every other `core` module reads on demand — rather than threading settings through every model that will ever use it (Part 29's `users.mfa_secret`, later provider tokens). A **separate** required key from `app_secret_key` (fail-fast, same min-length rule) so rotating one never touches the other. **`core/idempotency.py`** — an `Idempotency-Key` header facility (§9). Implemented as `IdempotentRoute`, an `APIRoute` subclass (not a dependency): a dependency runs *before* the handler and never sees what it returned, while overriding `get_route_handler()` wraps the whole request→response cycle, which is what makes caching the *actual* response possible. Cache key is `tenant + actor (bearer header, or "anon" for the unauthenticated capture surfaces) + route + key` in Redis: first request takes a `SET NX` lock (`__in_progress__`, 30s), executes, and caches the real response (status/media-type/body) for `idempotency_key_ttl_seconds` (24h) on any non-5xx result — a 5xx frees the key instead, since a server error isn't a result worth replaying and the caller should get a fresh attempt. A concurrent duplicate (lock already held) raises the new `IdempotencyConflictError` (409, slug `idempotency-key-in-flight`) rather than racing the handler twice. **Degrades open** exactly like the rate limiter (§10.2's stance, reused verbatim): any Redis failure (lock check, lock acquire, cache store) just lets the request execute normally rather than taking the endpoint down — this is a convenience against accidental duplicates, not a correctness guarantee that must hold when the cache itself is unavailable. **Wired onto the three named money/duplicate-sensitive POSTs**, each via a sibling router rather than modifying the existing one: `include_router()` can't override a single route's class, and `@router.post()`'s decorator sugar doesn't expose FastAPI's `route_class_override` (only `add_api_route()` does), so each site gets a tiny same-prefix/same-tags/same-RBAC `APIRouter(route_class=IdempotentRoute)` holding just that one route — `leads.capture_idempotent_router` (`POST /leads/capture`), `appointments.booking_idempotent_router` (`POST /agents/{slug}/appointments` — the advisory-lock in `service.book()` already kills a true double-booking race for a *different* slot, this kills a client retry re-booking the *same* slot as a second row), `tenants.platform_billing_idempotent_router` (`POST /platform/tenants/{id}/checkout`, mirroring `platform_router`'s prefix + `PLATFORM_TENANT_VIEW` router-wide dependency exactly so RBAC doesn't drift between the two routers). All three added to `main.py`'s router composition alongside their non-idempotent siblings. Config added (both fail-fast/documented, none silently defaulted away): `field_encryption_key` (required, ≥32 chars) + `field_encryption_key_id` (default `v1`) + `field_encryption_keys` (default empty); `idempotency_key_ttl_seconds` (default 86400). `.env.example` gained a documented block; `tests/conftest.py` pins a test `FIELD_ENCRYPTION_KEY` alongside the existing `APP_SECRET_KEY`. - **Part 29 — Auth hardening: lockout, MFA, breach-check, OAuth seam (§7.1, §10.3, done, 2026-07-24):** the auth differentiators, extending `modules/auth` + `modules/users` (no new module). Migration 0023, two new `AppError` subclasses, two new deps (`pyotp`, `authlib`), three new files under `core/` + two new `integrations/` packages. **Account lockout (`core/lockout.py`, §7.1)** — the layer the rate limiter deliberately is *not*: `core.rate_limit` blunts volume and degrades open by design (§10.2), but five tries a minute from a rotating IP pool never trips a per-minute budget and still walks a password list. Two independent Redis counters per attempt — **per account** (`tenant + sha256(email)`, so a distributed run from many IPs is stopped) and **per source IP** (so one host cannot spray many accounts, each of which alone stays under its own threshold) — either being locked refuses the attempt, with **exponential backoff** (`base * 2 ** (failures - threshold)`, capped at `login_lockout_max_seconds` so a determined attacker cannot lock a real user out for days). The email is **hashed into the key**: Redis keys surface in `MONITOR`/`SLOWLOG`/RDB dumps and the set of accounts under attack is itself worth not leaking (same stance as Part 30's idempotency actor key). A successful login **resets both counters first** — otherwise someone who mistypes four times stays one slip from a lockout forever. Fails **open** on a Redis error like every other Redis touch point here, with the consequence stated explicitly in the module docstring (an outage leaves Argon2id + the rate limiter, which is exactly why lockout is one layer of several rather than the only one). Critically, **every failure path raises the same generic 401** — locked, unknown email, wrong password and disabled account are indistinguishable, so the lockout is felt as slowness and never read as "this address exists and your run is working" (§7.1 no-enumeration). **Breached-password check (`integrations/breach/hibp.py`, §10.3)** — HIBP's k-anonymity range API: the password is SHA-1'd *locally*, only the **first 5 hex chars** are sent, and the match is done here against the local digest, so HIBP learns a prefix shared by hundreds of thousands of passwords and nothing else (SHA-1 is the corpus's index format, not a security choice — storage is still Argon2id). `Add-Padding: true` is requested and count-0 decoy rows are correctly *not* treated as hits. **Fail-open, deliberately and documented**: disabled, timeout, transport error, non-200 and unparseable body all return "not breached" — blocking every signup and reset because a free third-party API is down would be a self-inflicted outage traded against a probabilistic improvement in password quality; this is a filter on bad choices, not an authentication control. Wired on register **and** password reset, where the check runs **before the single-use reset code is consumed** — a rejected new password must not burn the code, or a typo in the *replacement* locks the person out of their own recovery flow. New `BreachedPasswordError` → 422 `breached-password` (the payload is what's wrong and the caller fixes it by choosing differently; a distinct slug lets a frontend show the specific hint instead of a generic validation blob). **MFA/TOTP (§7.1)** — `core/mfa.py` wraps pyotp so the algorithm lives in one place and the auth service never imports the library; the secret is **field-encrypted at rest with Part 30's `EncryptedString`** (§10.7 — this is the consumer that motivated the 30-before-29 dependency ordering). The migration widens `users.mfa_secret` from `String(64)` to `String(255)`: the column was reserved in Part 3 for a plaintext 32-char base32 seed, but the `{key_id}:{b64(nonce+ct)}` envelope measures ~83 chars (verified empirically before writing the migration, not assumed). New `mfa_enabled` / `mfa_enrolled_at` split **"a secret exists" from "the factor is live"** — enrolment mints a secret but only a successful verify flips `mfa_enabled`, so an abandoned enrolment can never demand a factor the person cannot produce (tested). Re-enrolling while already enabled is allowed (a lost phone) but does **not** disable the live factor until the new one verifies, so a hijacked session cannot silently swap the second factor out. Flow: `POST /auth/mfa/enrol` → provisioning URI + secret (the one response that carries it, only ever to the already-authenticated owner) → `POST /auth/mfa/enrol/confirm` → `POST /auth/mfa/disable`, which **re-authenticates with the current password** (a stolen session must not be able to strip the very control protecting the account). At login the password step returns an `MfaRequiredOut` **with no access token and no refresh cookie** instead of a session; the short-lived `mfa_token` ticket is stored hashed in Redis, **pinned to the tenant** (a ticket minted on agency A cannot be redeemed on B — tested), and **consumed with `GETDEL` *before* the code is checked**, so one ticket buys exactly one guess — otherwise a five-minute window would be a million free attempts at a six-digit code. **Enforcement for privileged roles is a prompt to enrol, not a hard login block** (`MFA_ENFORCED_ROLES`): flipping a hard requirement on would instantly lock out every existing admin, including the one who would have to fix it — decision documented at `_mfa_required`. **OAuth (`integrations/auth_oauth/`, seam only)** — a provider protocol + neutral `OAuthProfile` + `OAuthError(permanent=...)` (the same validation-vs-transport split as the AI/billing/portal seams), a Google adapter via authlib's `AsyncOAuth2Client`, and a registry that returns **`None`** without credentials. New `FeatureNotConfiguredError` → **501** `feature-not-configured` (not 404: the route genuinely exists and is part of the API, it is the *implementation* that is absent on this deployment — that distinction is what lets a frontend tell "this build cannot do it" from "you typed the wrong URL", and unlike a 503 it never invites a retry). `GET /auth/oauth/providers` returns `[]` so a frontend renders no button rather than one that 501s when clicked. State is a single-use Redis CSRF nonce pinned to tenant+provider. Account linking has three ordered cases with one security-critical rule: an existing link wins outright; otherwise a same-email account is linked **only if the provider says it verified that address** (an unverified provider email is an account-takeover primitive — claim someone's address at the provider, then sign in as them here), else 409; otherwise a new self-registration-tier account with an unusable random password. **Session list (§10.3)** — `sessions.last_used_at` added (a device list is only usable if the rows are distinguishable); `GET /auth/sessions` lists live rows (revoked/expired excluded — a dead row is only noise) each flagged `current` by matching the **presented refresh token's hash** (the access jti is not on the session row; the refresh chain is what actually identifies a device), carrying **no token material at all**; `DELETE /auth/sessions/{id}` is scoped to the caller's own rows and **404s for anyone else's**, so the endpoint is not an oracle for which session ids exist.
